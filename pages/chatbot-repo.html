OPTIONAL · ADVANCED PROJECT

Build a private, API-driven school chatbot

Want a chatbot that never trains on student data and lives entirely under your school's control? This optional project builds one using an API key, no student data ever leaves your system, and nothing trains a model. Great for tech-minded teachers or a club.

No training API-driven Cloneable repo Advanced

Why build your own?

Why a private chatbot is worth considering

Privacy by design

An API call doesn't train the model on your input. Your conversation isn't added to anyone's training set.

You control it

It's your code, your account, your rules. No surprise policy changes.

A learning opportunity

Building it is a fantastic way to teach students how AI actually works under the hood.

Not for everyone

This requires some technical comfort. If that's not you, skip it. The web tools in the Toolbox are plenty.

The plan

How to build it, step by step

  1. Decide the approach

    Two options: (a) Local + free using Ollama (open-source models on a school computer, fully offline, $0), or (b) Cloud API using a paid API key from OpenAI/Anthropic/Google (higher quality, small per-use cost, still no training on your data).

  2. Set up a GitHub repository

    Create a repo (e.g., school-chatbot). Keep it private if it contains school specifics. This is the repo teachers (or students) can clone to run their own copy.

  3. Choose the interface

    A simple web page (HTML + a few lines of JavaScript) that talks to the model. Keep it minimal. The point is a working tool, not a fancy app.

  4. Add your API key (cloud option) or Ollama (local)

    For cloud: store the API key in a private environment variable, never commit it to the repo or put it in the HTML. For local: run Ollama on the school computer and point the page at it.

  5. Write a clear README

    So a colleague (or future you) can clone and run it in minutes. Include setup, the privacy note, and any costs.

  6. Test with teachers, then students

    Pilot with a small group first. Keep a human reviewing what it produces before it's used widely.

A working example

A minimal HTML chatbot (stub you can extend)

This is a simplified starting point. In a real setup you'd call the model's API from a small backend so your key isn't exposed in the browser. This stub shows the shape.

Security first

Never put a real API key in a web page teachers/students open. Route calls through a small server or serverless function that holds the key.

<!-- chat.html (conceptual stub) -->
<form id="chat">
 <label>Your question:</label>
 <input id="q" placeholder="Ask the model...">
 <button>Ask</button>
</form>
<pre id="out">
<script> // In production, this calls YOUR backend, which holds the API key. // The key must NEVER live in this file. const out = document.getElementById("out"); document.getElementById("chat").addEventListener("submit", async (e) => { e.preventDefault(); const q = document.getElementById("q").value; out.textContent = "Thinking..."; const res = await fetch("/api/ask", { // your backend endpoint method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ question: q }) }); const data = await res.json(); out.textContent = data.answer; }); </script>

The backend (/api/ask) is where you add the real model call and hold your key securely.

The details

Privacy & cost at a glance

Privacy

API calls are generally not used to train models (that's the whole point of the paid API). Still, don't paste student PII, keep it to lesson content, not identifiable info. For the strongest privacy, use Ollama locally so nothing leaves the machine at all.

Cost

Ollama: $0 (free, open source). Cloud API: small per-use fees (a few cents per conversation typically, depending on the model). Free credits are often available for first-time API users. Set a hard monthly budget in the API dashboard.

Honest advice

When should you not build this?

You probably don't need it

For most schools, the free, school-approved tools in the Toolbox are more than enough. Build a private chatbot only if you (a) want total control, (b) have a technical champion, or (c) want it as a learning project for staff or students. It's a great "stretch goal," not a requirement.
